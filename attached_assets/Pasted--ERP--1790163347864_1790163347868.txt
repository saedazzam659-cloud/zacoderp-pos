المواصفات النهائية لتكامل المشاريع والعقود وبنود التنفيذ مع ERP
الهدف
إعادة تنظيم دورة المقاولات وإدارة المشاريع مع الحفاظ على الشاشات والبيانات الحالية وعدم إنشاء نظام مكرر لبنود التنفيذ.
القاعدة الأساسية:
المشروع → العقود → بنود العقود → التنفيذ → المستخلصات والتكاليف → التقارير والربحية
مع دعم:
مشروع رئيسي.
مشاريع فرعية.
أكثر من عقد داخل المشروع الواحد.
عقد مالك.
عقود مقاولين من الباطن.
بنود مختلفة لكل عقد.
ربط كامل بالمخازن والمشتريات وHR/Payroll والأصول والمصروفات والمحاسبة.
منع تكرار البيانات والتكاليف والقيود المحاسبية.

1. المشروع هو المركز الرئيسي
يجب اعتبار المشروع هو الـParent الرئيسي في موديل المقاولات وإدارة المشاريع.
المشروع الواحد يمكن أن يحتوي على:
عقد مالك واحد أو أكثر حسب احتياج النظام.
عقد أو عدة عقود مقاولين من الباطن.
عقود توريد أو عقود أخرى حسب أنواع العقود الموجودة بالنظام.
مستخلصات متعددة لكل عقد.
تكاليف متعددة مرتبطة بالمشروع والعقد وبند العقد.
العلاقة الأساسية:
مشروع → عدة عقود
ولا يتم افتراض أن المشروع مرتبط بعقد واحد فقط.

2. دعم المشروع الرئيسي والمشاريع الفرعية
يجب دعم:
مشروع رئيسي ↓ مشاريع فرعية
مثال:
مشروع رئيسي: إنشاء مجمع صناعي
مشاريع فرعية:
مبنى الإدارة.
المصنع.
المخازن.
أعمال البنية التحتية.
المشروع الفرعي يمكن أن يحتوي على عقوده ومستخلصاته وتكاليفه بشكل مستقل.
ويجب إمكانية عرض التقارير:
على مستوى المشروع الفرعي.
أو تجميع جميع المشاريع الفرعية على المشروع الرئيسي.
لمنع التعقيد، يتم دعم مستويين فقط حاليًا:
مشروع رئيسي → مشروع فرعي
ولا يتم إنشاء تسلسل لا نهائي للمشاريع.

3. لا يتم إنشاء شاشة بنود تنفيذ موازية للعقد
هذه نقطة أساسية.
بما أن النظام الحالي يحتوي بالفعل على بنود داخل العقد، فلا يتم هدمها أو نقلها إلى نظام جديد.
يجب الحفاظ على بنود العقد الحالية وتطوير العلاقات حولها.
بالتالي:
البند الموجود داخل العقد = بند العقد الفعلي
ولا نطلب من المستخدم إدخال نفس البند مرة أخرى داخل شاشة مستقلة.

4. مكتبة بنود التنفيذ - اختيارية
إذا كانت هناك حاجة مستقبلية إلى مكتبة عامة لبنود التنفيذ، يمكن الاحتفاظ بها كـ:
Execution Item Templates / مكتبة قوالب بنود
ولكنها ليست مصدرًا إجباريًا للتعاقد.
وظيفتها فقط:
تسريع إنشاء بنود العقود.
إعادة استخدام البنود المتكررة.
توحيد أسماء البنود والوحدات.
تقليل إعادة الكتابة.
عند اختيار قالب:
يتم نسخ بيانات التعريف فقط إلى بند العقد.
ولا يتم إنشاء Master Data مكرر للتنفيذ.

5. بيانات المشروع
يجب أن يحتوي المشروع على:
كود المشروع.
اسم المشروع.
المشروع الرئيسي إن وجد.
نوع المشروع.
العميل/المالك.
الموقع.
تاريخ البداية.
تاريخ النهاية.
مدير المشروع.
الحالة.
الملاحظات.
البيانات الحالية الموجودة في النظام.
ويجب عدم إنشاء بيانات عميل أو موظف أو مورد جديدة داخل المشاريع.

6. ربط العقود بالمشروع
يجب إضافة:
Project ID
إلى كل عقد.
كل عقد يجب أن يكون مرتبطًا بمشروع محدد.
أنواع العقود الحالية تظل كما هي، مثل:
عقد المالك.
عقد مقاول باطن.
عقد توريد.
أي أنواع عقود أخرى موجودة بالنظام.
العلاقة:
Project ↓ Contracts
ويسمح للمشروع الواحد بأكثر من عقد.

7. عقد المالك
عند إنشاء عقد مالك:
اختيار المشروع → إنشاء عقد المالك → إضافة بنود العقد
يتم الاحتفاظ بكل بيانات العقد الحالية، مثل:
رقم العقد.
تاريخ العقد.
العميل/المالك.
قيمة العقد.
مدة العقد.
الشروط.
الدفعة المقدمة.
نسبة الاحتجاز.
البنود.
الكميات.
الأسعار.
الخصومات.
الإضافات.
ولا يتم إنشاء عقد خارج مشروع.

8. عقد المقاول من الباطن
نفس النظام:
اختيار المشروع → اختيار المقاول → إنشاء عقد المقاول من الباطن → إضافة البنود
المقاول من الباطن يتم اختياره من بيانات الموردين/المقاولين الموجودة بالنظام.
ولا يتم تسجيله كموظف في HR.

9. بنود العقد
كل عقد يحتفظ ببنوده الخاصة.
مثال:
المشروع: إنشاء مصنع X
عقد المالك:
أعمال خرسانة.
أعمال مباني.
أعمال سباكة.
أعمال كهرباء.
عقد مقاول الباطن:
أعمال سباكة.
أعمال كهرباء.
قد يكون نفس العمل موجودًا في أكثر من عقد، لكن لكل عقد بياناته التعاقدية الخاصة.

10. بيانات بند العقد
يجب الحفاظ على بنية بنود العقد الحالية، وإتاحة:
اسم البند.
كود البند.
الوصف.
الوحدة.
الكمية.
سعر الوحدة.
القيمة.
الخصم.
الإضافة.
الملاحظات.
أي بيانات إضافية موجودة حاليًا.
ولا يتم إنشاء نسخة ثانية من البند لمجرد استخدامه في عقد آخر.

11. الفرق بين بند التنفيذ وبند العقد
إذا كانت هناك مكتبة قوالب:
Execution Item Template = قالب قابل لإعادة الاستخدام.
أما:
Contract Item = البند الفعلي الموجود داخل عقد معين.
مثال:
القالب: أعمال سباكة – توريد وتركيب
عقد المالك: 1000 نقطة × 500 = 500,000
عقد المقاول من الباطن: 1000 نقطة × 350 = 350,000
الاثنان مرتبطان بنفس المشروع، لكن لكل عقد بياناته التعاقدية.

12. عدم تكرار البند عند إنشاء عقد
عند إضافة بند داخل العقد:
يمكن اختيار بند موجود.
أو اختيار قالب من مكتبة القوالب إن كانت موجودة.
أو إدخال بند العقد بالطريقة الحالية إذا كانت الشاشة الحالية تسمح بذلك.
المهم:
لا يتم إنشاء Master Data جديدة داخل المقاولات لكل عقد.
ويجب الحفاظ على البيانات الحالية عند التعديل.

13. أنواع التنفيذ
يجب أن يدعم النظام عند الحاجة:
توريد فقط.
عمالة/تنفيذ فقط.
توريد وتركيب.
توريد + عمالة.
توريد + عمالة + معدات.
أعمال مركبة.
مقاول باطن.
ولا يعني نوع "مقاول باطن" أن المقاول موظف.

14. مكونات تكلفة بند العقد
بند العقد يمكن أن تكون تكلفته الفعلية مكونة من:
مواد.
عمالة.
معدات.
إهلاك.
مشتريات.
مقاول باطن.
مصروفات مباشرة.
لكن هذه المكونات لا يتم تسجيلها يدويًا كنظام مستقل.
بل تأتي من الأنظمة الحالية.

15. المواد والمخازن
إذا تم استخدام مواد في تنفيذ بند:
يتم استخدام الأصناف الموجودة بالفعل في Inventory.
الدورة:
Inventory → حركة المخزن → المشروع → العقد → بند العقد
ويجب أن تؤثر الحركة فعليًا على المخزون والتكلفة.
لا يتم إنشاء أصناف جديدة داخل المقاولات.

16. المشتريات
إذا تم شراء مادة للمشروع:
Purchasing → المورد → فاتورة/استلام → مخزون أو مصروف → المشروع → العقد → بند العقد
ولا يتم إنشاء فاتورة شراء ثانية داخل المقاولات.

17. العمالة
العمالة تستخدم بيانات HR/Payroll الحالية.
لا يتم إنشاء موظفين داخل المقاولات.
التكلفة يمكن توزيعها حسب:
ساعات العمل.
الأيام.
النسب.
بيانات التنفيذ.
الآلية الحالية الموجودة بالنظام.
العلاقة التحليلية:
الموظف → المشروع → العقد → بند العقد
مع منع Double Counting.

18. المعدات والأصول
إذا تم استخدام معدة مملوكة للشركة:
يتم اختيارها من Fixed Assets.
لا يتم إنشاء جدول معدات مستقل إذا كانت الأصول موجودة بالفعل.
العلاقة:
الأصل → المشروع → العقد → بند العقد → الاستخدام → التكلفة

19. إهلاك المعدات
يجب استخدام نفس Logic الإهلاك الموجود حاليًا في:
Fixed Assets / Manufacturing
ولا يتم إنشاء Logic إهلاك مستقل للمقاولات.
إذا كان الإهلاك مسجلًا بالفعل:
يتم تحميل الجزء المستخدم على المشروع/العقد/البند وفق آلية التوزيع.
مثال:
إهلاك المعدة = 30,000
استخدام المشروع = 60%
التكلفة المحملة = 18,000
أو حسب ساعات التشغيل إذا كان هذا هو النظام الحالي.
ويجب منع تسجيل الإهلاك مرتين.
إذا كانت هناك Function/API مستخدمة حاليًا في التصنيع لحساب الإهلاك أو تكلفة استخدام الأصل، يجب إعادة استخدامها أو تعميمها.

20. المصروفات
المصروفات المباشرة تستخدم نظام Expenses/Accounting الحالي.
مثل:
نقل.
وقود.
أدوات.
خدمات.
مصروفات موقع.
إيجار معدات.
مصروفات أخرى.
ويتم ربط المصروف تحليليًا بـ:
المشروع → العقد → بند العقد
حسب طبيعة العملية.

21. المقاول من الباطن
الدورة:
المشروع → عقد المقاول من الباطن → بند العقد → كمية التنفيذ → المستخلص → الاعتماد → تكلفة المشروع
ولا يتم إنشاء كيان جديد للمقاول إذا كان موجودًا بالفعل كمورد/مقاول.

22. المستخلصات - التعديل الأساسي
هذه نقطة أساسية جدًا.
لا يبدأ المستخلص باختيار العقد مباشرة.
يجب أن يكون التسلسل:
اختيار المشروع ↓ عرض العقود التابعة للمشروع ↓ اختيار العقد ↓ عرض بنود العقد ↓ إنشاء المستخلص
وبذلك يصبح المشروع هو نقطة البداية.

23. منع اختيار عقد تابع لمشروع آخر
إذا اختار المستخدم:
المشروع A
فلا تظهر له إلا العقود المرتبطة بالمشروع A.
ولا يسمح النظام بربط مستخلص المشروع A بعقد تابع للمشروع B.
يجب تطبيق هذا التحقق في:
Frontend.
Backend.
Database Relations عند الإمكان.
ولا يعتمد النظام على حماية الواجهة فقط.

24. المستخلص يعتمد على بنود العقد
بعد اختيار:
المشروع → العقد
يعرض النظام بنود العقد فقط.
لا يمكن إنشاء مستخلص لبند غير موجود في العقد.
بيانات المستخلص:
الكمية السابقة.
الكمية الحالية.
الإجمالي.
نسبة الإنجاز.
قيمة التنفيذ.
الخصومات.
الإضافات.
الدفعة المقدمة.
نسبة الاحتجاز.
صافي المستخلص.
أي عناصر موجودة حاليًا بالنظام.

25. اعتماد العقود
يمكن السماح بحفظ العقد كـDraft إذا كان النظام يحتاج ذلك.
لكن:
لا يسمح باعتماد العقد بدون بند واحد على الأقل.
رسالة النظام:
"لا يمكن اعتماد العقد قبل إضافة بند تنفيذ واحد على الأقل."
ولا يسمح ببدء التنفيذ على عقد غير معتمد.
ولا يسمح بإنشاء مستخلص على عقد غير معتمد.

26. تكلفة البند
يجب حساب التكلفة الفعلية للبند من المصادر الفعلية:
مواد.
عمالة.
معدات.
إهلاك.
مشتريات.
مقاول باطن.
مصروفات مباشرة.
ثم:
التكلفة الفعلية للبند
مقابل:
القيمة التعاقدية للبند
لإظهار ربحية البند.

27. عدم إدخال تكلفة المواد يدويًا
إذا تم صرف مواد من المخزن:
لا يقوم المستخدم بإدخال تكلفة المادة يدويًا داخل المقاولات.
الحركة الأصلية من Inventory هي مصدر التكلفة.
وبالتالي:
المخزون ينخفض → التكلفة تسجل → ترتبط بالمشروع والعقد والبند
مع منع تسجيل التكلفة مرة أخرى.

28. منع Double Counting
يجب تطبيق قاعدة عامة:
إذا قامت الوحدة الأصلية بتسجيل التكلفة أو القيد المحاسبي، لا تقوم المقاولات بتسجيله مرة أخرى.
مثال:
Payroll سجل تكلفة الموظف.
المقاولات تقوم بالتوزيع التحليلي فقط وفق الآلية المعتمدة.
Fixed Assets سجل الإهلاك.
المقاولات تقوم بتحميل الجزء المستخدم فقط.
Inventory سجل تكلفة الصرف.
المقاولات لا تنشئ تكلفة مواد ثانية.
Accounting يستقبل القيد الأصلي ولا يتم إنشاء قيد مكرر.

يجب توفير التقارير على مستويات متعددة:
مستوى البند
قيمة العقد.
الكمية التعاقدية.
الكمية المنفذة.
التكلفة التقديرية.
التكلفة الفعلية.
المواد.
العمالة.
المعدات.
الإهلاك.
المقاول من الباطن.
المصروفات.
الربحية.
مستوى العقد
تجميع جميع بنود العقد.
مستوى المشروع الفرعي
تجميع جميع عقود المشروع الفرعي.
مستوى المشروع الرئيسي
تجميع جميع المشاريع الفرعية والعقود التابعة لها.

30. الهيكل النهائي للعلاقات
الشركة ↓ المشروع الرئيسي ↓ المشاريع الفرعية ↓ العقود ├── عقد المالك ├── عقود المقاولين من الباطن └── أنواع العقود الأخرى ↓ بنود العقد ↓ التنفيذ والمستخلصات ↓ مصادر التكلفة ├── Inventory ├── Purchasing ├── HR/Payroll ├── Fixed Assets ├── Subcontractors └── Expenses ↓ Accounting ↓ التكلفة والربحية

31. التقارير التجميعية
يجب أن يستطيع النظام الانتقال من:
المشروع الرئيسي ↓ المشروع الفرعي ↓ العقد ↓ بند العقد ↓ التنفيذ ↓ التكلفة
مع إمكانية معرفة مصدر كل رقم وتكلفة.
مثال:
مشروع رئيسي = 10 مليون
المشروع الفرعي الأول = 4 مليون
المشروع الفرعي الثاني = 6 مليون
ويمكن الدخول إلى أي مستوى لمعرفة تفاصيله.

32. قاعدة عدم تكرار Master Data
ممنوع إنشاء Master Data جديدة داخل المقاولات للبيانات الموجودة بالفعل.
لا يتم تكرار:
الأصناف.
المخازن.
الموظفين.
الموردين.
العملاء.
المقاولين.
الحسابات.
الأصول.
المصروفات.
الرواتب.
المقاولات تستخدم البيانات الحالية عن طريق:
Relations + APIs

33. التكامل المحاسبي
مصدر التكلفة | النظام
المواد | Inventory
المشتريات | Purchasing
العمالة | HR/Payroll
الأصول | Fixed Assets
الإهلاك | Fixed Assets
المقاول من الباطن | Subcontractor Contract/Certificate
المصروفات | Expenses
القيود | Accounting
ولا يتم إنشاء قيد محاسبي مكرر إذا كانت العملية الأصلية قامت بإنشاء القيد.

35. الحفاظ على البيانات الحالية
ممنوع:
حذف العقود الحالية.

حذف المشاريع الحالية.
حذف المستخلصات الحالية.
تكرار البيانات.
تغيير البيانات التاريخية بدون Migration آمن.
أي تعديل في Database يجب أن يكون:
Migration آمن + Backup + الحفاظ على العلاقات والبيانات الحالية.

36. عدم كسر الوظائف الحالية
ممنوع كسر أي وظيفة تعمل حاليًا، خصوصًا:
العقود.
بنود العقود.
المستخلصات.
المخازن.
المشتريات.
HR.
Payroll.
Fixed Assets.
Accounting.
Manufacturing.
أي تعديل يجب أن يكون متوافقًا مع النظام الحالي.

37. الاختبارات النهائية
يجب اختبار:

النتيجة النهائية المطلوبة
يجب أن تصبح المشاريع هي المركز الرئيسي في موديل المقاولات.
المشروع الرئيسي ↓ المشاريع الفرعية ↓ عدة عقود ↓ بنود كل عقد ↓ التنفيذ ↓ المستخلصات ↓ مصادر التكلفة ↓ Accounting ↓ تكلفة وربحية البند ↓ تكلفة وربحية العقد ↓ تكلفة وربحية المشروع الفرعي ↓ تكلفة وربحية المشروع الرئيسي
ولا يتم إنشاء نظام جديد يكرر وظيفة العقود أو بنود العقود الحالية.
إذا كانت هناك حاجة إلى مكتبة عامة لبنود التنفيذ، تكون اختيارية كقوالب مساعدة وليست نظامًا موازيًا أو شرطًا لإدارة العقود.
قاعدة التنفيذ النهائية
Integration وليس إنشاء ERP فرعي داخل موديل المقاولات.
يجب إعادة استخدام:
Inventory Purchasing HR/Payroll Fixed Assets Accounting Manufacturing Logic Projects Contracts Existing Contract Items Existing Progress Certificates
ولا يبدأ أي تعديل Database أو Backend قبل فحص البنية الحالية والـAPIs والـLogic الموجود.
الأولوية: الحفاظ على البيانات الحالية، عدم تكرار الوظائف، وربط المشروع بالعقود والمستخلصات والتكاليف بشكل صحيح.
