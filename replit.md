# ZATCA e-invoicing System

This application provides a comprehensive Saudi ZATCA e-invoicing system to optimize financial operations, automate accounting, and ensure ZATCA compliance for multi-company businesses.

## Architecture decisions

- **Modular Monorepo**: Uses pnpm workspaces for code reusability and clear separation of concerns, housing both frontend and backend services.
- **Multi-Tenancy**: Database schema and API design inherently support multi-company operations with `company_id` for data isolation and granular RBAC.
- **ZATCA Compliance**: Deep integration for ZATCA e-invoicing, including CSR/CSID management, UBL 2.1 XML generation, and TLV QR codes.
- **Strategic AI Integration**: AI is used for advanced analytics (e.g., sales reports, cost center analysis), content generation (e.g., product descriptions), and operational assistance with rule-based fallbacks.
- **Realtime Session Synchronization**: Utilizes Server-Sent Events (SSE) for immediate propagation of critical SuperAdmin changes (e.g., subscription, company state) to logged-in users, enhancing responsiveness.
- **SAP-style Production WIP Cycle**: Production orders post a full DR WIP / CR Raw inventory journal entry on `in_production` (with header‑level labor + overhead allocation), and DR Finished Goods (+ DR Variance/Waste) / CR WIP on `completed`. Finished‑goods unit cost is `wipBalance × producedQty / (producedQty + wasteQty)`. Cancelling an issued order auto‑reverses the issue. Header `costCenter` propagates to every JE line. Warehouse + account fields lock once issue is posted.
- **JE Explicit-Save Reservation**: The journal-entry form does NOT reserve a number on mount — opening "قيد جديد" and closing the tab leaves NO row in `journal_entries` and NO gap in the sequence. The badge above the form shows the next-estimated number via `useNextSequenceNumber` (peek-only). Clicking "حفظ" atomically consumes the number through `nextSequenceNumber(cid, "journal_entry", …)` inside `POST /api/journal-entries/`; the same endpoint accepts unbalanced / under-populated entries and persists them as `status='draft'` (balanced + ≥2 valid lines → `status='posted'`, honouring the per-company auto-post toggle via `resolvePostingStatus`). There is no `/reserve` endpoint and no `journalEntriesApi.reserve` helper — both were removed. The form has no `beforeunload`/unmount cleanup because nothing needs cleaning. Drafts created here remain valid and can be completed/posted later from مركز الترحيل; per the "Posted-Only Financial Reports" rule they have ZERO impact on reports until posted.
- **Sister Companies (الشركات الشقيقة)**: Dedicated `sister_companies` + `sister_transfers/_items` + `sister_returns/_items` + `sister_settlements` tables — NOT customers (sister cos share the user's VAT/CR so ZATCA would reject them as a customer). Module key `sister_companies`, **locked by default** (option B) — SuperAdmin must enable per company via `/admin/menu-permissions`; no parent billable module. JE per transfer post: DR COGS(cost) + DR SisterAR(supply) / CR Inventory(cost) + CR Revenue(supply); stock-ledger out. Return post reverses the exact accounts and restores stock at original cost. Settlement is bidirectional: `direction='receive'` → DR cash/bank / CR SisterAR, `direction='pay'` → DR SisterAR / CR cash/bank (entryType `sister_settlement`). No VAT (internal), SAR only, no UBL/QR/ZATCA submission. Statement report mirrors CustomerStatement with the sister-co AR account. Routes mounted at `/api/sister-companies/*`; UI under `/inventory/sister-*` (4 sidebar entries). **Express 5 / path-to-regexp 8 quirk**: `/:id`, `/:id/balance` are registered LAST in `routes/sister-companies.ts` (after `/transfers`, `/returns`, `/settlements`) — inline regex like `/:id(\d+)` is no longer supported, so registration order is the only thing that prevents `:id` from swallowing the literal sub-segments.
- **Header Warehouse Picker on Document Forms**: All 8 document forms — sales invoice / quotation / order (shared `SalesDocumentForm.tsx`), `PurchaseInvoiceForm.tsx`, `PurchaseOrderForm.tsx`, `GoodsReceipts.tsx`, `GoodsDeliveries.tsx`, `SalesReturns.tsx`, `PurchaseReturns.tsx` — expose a header-level "المستودع" `SearchCombobox`. On new docs it auto-selects the company's default warehouse (`warehouses.find(isDefault) ?? warehouses[0]`); on edit it derives from the first line that already has a `warehouseId`. Changing the header picker broadcasts to **every** line (`setLines(prev => prev.map(l => ({ ...l, warehouseId: v })))`) via an `applyHeaderWarehouse(v)` helper. A third effect back-fills any lines with empty `warehouseId` from the header value (so newly-added lines inherit it). This replaces the older per-line `defaultWarehouse` auto-fill effects. GoodsReceipts/GoodsDeliveries use a `form/setForm` state pattern (not separate states) and additionally clear `headerWarehouseId` on `!showForm` so re-opening the create form starts fresh. No API/schema changes — lines already carried `warehouseId`.
- **POS Desktop — Offline Tauri Windows app** (`artifacts/pos-desktop/`, separate from web POS at `artifacts/pos/`): Tauri+React+SQLite app for `zacoderp.com`, feature-flagged via `companies.enable_offline_pos`. **Two-mode boot** via FirstRunWizard: **(cloud)** device-license activation (Ed25519-signed JWT, hardware-fingerprint-bound, `FOR UPDATE` race-safe) → cashier login (3-step: creds → branch → terminal) → SalesScreen, with `/api/sync/{heartbeat,pull,push}` + `/api/device-licenses/{activate,validate,deactivate}`; **(standalone)** Ed25519-signed `.zacolic.json` license file → local bcrypt-hashed users in SQLite, **zero cloud calls**. Per-machine **vertical** (general/grocery/pharmacy) set at first run, gates pharma-only UI + EDA catalog import + 14% VAT default. Scale integration: serial readout (CAS/Bizerba/GenericAscii) + embedded-weight EAN-13 barcode parsing. **Parked carts** are device-only, scoped by `pos_session_id`, never pushed to cloud. SuperAdmin UI at `/admin/{pos-devices,offline-licenses}` uses direct fetch+Bearer (admin convention, not generated client). Public download at `/download` with per-country MSI URLs. MSI build via `.github/workflows/pos-desktop-build.yml` on `windows-latest` — produces draft GitHub Release on `pos-desktop-v*` tag push; signing opt-in via `WINDOWS_CERT_*` secrets; offline-license pubkey injected via `OFFLINE_LICENSE_PUBLIC_KEY_B64` build secret. See `.agents/memory/` files: `pos-desktop-two-auth-layers`, `pos-desktop-parked-carts`, `pos-desktop-sticky-footer`, `pos-desktop-pull-must-persist`, `pos-desktop-overlay-pattern`, `windows-openssl-trap`.
- **Account Notes Extended Metadata**: The 4 إشعارات (دائنة/مدينة عملاء وموردين) routes all render the same `AccountNoteForm.tsx`. The form now carries 5 extra columns on `account_notes` mirroring the voucher form: `operation_number`, `reference_number`, `reference_date`, `cost_center` (text, stores CC **code** — matches `journal_entries_lines.cost_center` convention), `project_id` (soft ref to `contracting_projects.id`, no FK — same pattern as `partyId`). The header `costCenter` is propagated to every JE line on post so cost-centre filtered reports pick the note up. Party tax number (الرقم الضريبي) is **derived/displayed only** from the selected customer/supplier — no extra column. All textboxes are constrained to `md:max-w-[50%]` (half their previous visible width) without changing the 2-col grid layout. Editing the route uses `b.X !== undefined` guards so omitted fields preserve existing values.
- **POS Desktop — ZATCA Bridge for Back-office Sales Invoices**: Back-office sales invoices (`SalesInvoicesAdmin` → `sales_invoices_local`) now also reach ZATCA by **reusing the POS register's existing pipeline** rather than building a second one. `lib/zatcaBridge.ts` (`isZatcaCountry()` + `bridgeSalesInvoiceToZatca()`) builds the same `OfflineInvoicePayload` (SAR base), generates the TLV QR (seller from `appSettings`), and `saveOfflineInvoice`s it into `offline_invoices` — which `/api/sync/push` carries to the cloud for ZATCA submission, unchanged. The two tables stay **physically separate** (no merge): `sales_invoices_local` keeps its rich accounting JEs; two additive columns (`zatca_qr_base64`, `zatca_offline_uuid`) + the `sales_invoice_set_zatca` command link the offline row back. **Build the QR/payload from the PERSISTED invoice** (`getSalesInvoice(id)` authoritative totals), NOT the form, to avoid rounding/FX drift between the QR and what `sales_invoice_create` stored. Idempotency key `sinv-<id>` → a bridge retry reuses the same `offline_invoices` row (no duplicates); the create + discount write are skipped on retry via `savedId`. Gated to `country == "SA"` (absent key defaults to "SA", matching `taxSettings.ts`). Bridge failure is **non-fatal** (invoice already saved) → Arabic warning, form stays open for retry. `zatcaQrBase64` is TLV printer data (not a renderable image); `SalesInvoicesAdmin` shows a ZATCA status badge/column instead. All changes confined to `artifacts/pos-desktop`. See `.agents/memory/pos-desktop-zatca-bridge.md`.
- **Manufacturing Master Data (Phase A)**: BOM Templates (`bom_templates` + `bom_template_lines`) define standard raw materials per FG product. On production order creation, if an active template exists for the chosen `productItemId`, raw lines are auto‑copied into the order with quantities scaled by `plannedQty / template.outputQty`. Per-company defaults live in `manufacturing_settings` (raw/FG warehouses, cost center, 7 GL accounts) and are applied when matching fields are omitted from POST `/api/production/orders`. Manage via `/production/bom-templates` and `/production/settings`.

## Gotchas

- **Branch-Level Data Isolation**: For users with `view_all_branches=false`, data is scoped to assigned branches across `/api/org/branches`, `/api/cash-boxes`, `/api/bank-accounts`, `/api/inventory/warehouses`, and the branch-linked LIST endpoints `/api/journal-entries`, `/api/account-notes`, `/api/pos-sessions`, `/api/fixed-assets/assets` (all use `branchScopeSpread(req, table.branchId, req.query.branchId)` from `middleware/auth.ts`). Shared rows (NULL `branch_id`) are read-only for restricted users. NOTE: `cash_transfers` has **no** `branch_id` column, so it is intentionally NOT branch-scoped — scoping it needs a schema change + a from-branch/to-branch design decision. **Branch filter semantics**: when an explicit `?branchId=X` is passed (or implied by user scope), `effectiveBranchCondition` matches `branch_id = X OR branch_id IS NULL` — NULL-branch rows are company-wide/shared (opening JEs, system-generated entries, shared resources) and must remain visible from any branch context. Otherwise picking the only branch in a single-branch company would yield different totals than "all branches" because NULL rows would be silently excluded.
- **Mandatory Warehouse Branch**: Saving a warehouse (create AND edit) now REQUIRES a branch — there are no more shared/NULL-branch warehouses created via the UI. Frontend (`inventory/Warehouses.tsx`) validates `branchId` before submit (switches to the "basic" tab + toast, "*" marker, no empty option in the branch combobox); backend `assertWarehouseBranchWritable` in `routes/inventory.ts` (shared by POST + PUT `/warehouses`) rejects null/empty `branchId` with `400 "اختيار الفرع إجباري"` for admin/viewAll users too (restricted users were already rejected). Pre-existing NULL-branch warehouses stay readable but must be assigned a branch the next time they are edited.
- **Editable Manager Username**: A company user's `username` can now be changed from `/users` (the field is no longer locked in edit mode). PATCH `/api/users/:id` accepts `username`, trims it, rejects empty (400), and enforces per-company uniqueness excluding self (409 on conflict) — mirroring the create handler's scope.
- **Posted Invoice Lock**: Sales and purchase invoice edit screens become read-only (`<fieldset disabled>`) when `existing.status === "posted"`. Modifications require unposting via specific API endpoints.
- **LC Expense Currency Default**: When adding an expense to an LC, if the LC currency is not the company's base currency, the `currencyCode` for the new expense defaults to the **base currency (SAR) with rate=1**. Server-side guards enforce `exchangeRate=1` for base currency entries.
- **Posted-Only Financial Reports**: Trial Balance, Balance Sheet, Income Statement, and Account Statement (`/api/reports/trial-balance`, `/balance-sheet`, `/income-statement`, `/account-statement`) include only journal entries with `status = 'posted'`. Draft (unposted) entries are work-in-progress and have **zero** impact on any financial report — opening, period, closing, running balance, and previous balance all ignore them. Unposting an entry (`POST /api/journal-entries/:id/unpost` flipping status `posted → draft`) instantly removes its impact from every report on the next refresh. System-generated JEs (sales/purchase invoices, vouchers, POS, payroll, production, stock movements) are inserted as `posted` directly, so this filter only affects manually-created draft JEs and entries explicitly unposted via the API.
- **Period Closing Cycle (IFRS-aligned)**: The fiscal-period close has 5 independent steps: validate → close-pl → transfer-profit → soft-close → hard-close. **Soft-close** rejects when revenue/expense accounts still have non-zero balances (`requiresPlClose: true` in the response) unless `force=true` is passed — needed for monthly soft-closes where P&L closes only at year-end. **Hard-close** has NO `force` override — it requires both a `closing_revenue`/`closing_expense` JE AND a `closing_transfer_profit`/`closing_transfer_loss` JE to exist for the period (skipped only when there was zero P&L activity). Recovery from a prematurely hard-closed period requires `POST /api/fiscal/periods/:id/force-reopen` (SuperAdmin only, requires a `reason` ≥ 10 chars, logged via `req.log.warn`). The standard `PATCH /periods/:id/status` still refuses to touch `permanently_closed` periods.
- **SuperAdmin Acting-Company Impersonation**: SuperAdmins can "enter" any tenant via `/admin/enter-company` (or the green button on `/companies`). Selecting a company writes its id to `localStorage.zatca_acting_company_id`, which `lib/api-client-react/src/custom-fetch.ts` auto-attaches to every generated-client request as the `x-acting-company-id` header. The server's `resolveCompanyId` (in `artifacts/api-server/src/middleware/auth.ts`) honours that header **only** when `req.user.role === "superadmin"`; an explicit `?companyId=` query still wins. A sticky amber banner in `Layout.tsx` (`<ActingCompanyBanner/>`) shows the active tenant + a one-click "خروج" that clears the key and invalidates **all** React Query caches (otherwise per-company data would bleed across tenants). The banner is also the only safe exit — never assume an SA is "in their own context" without checking `actingCompanyId` from `useAuth()`.
- **Customer Payment Terms (مدة الاستحقاق)**: `customers.payment_terms_days` (integer, nullable). When `> 0`, `POST /api/invoices` refuses a new CREDIT sales invoice for that customer if any prior posted credit invoice still has an outstanding balance AND is older than the term (counted from the *new* invoice date). FIFO-applies posted receipt vouchers + posted credit sales returns to the customer's prior posted credit invoices oldest-first, then checks the oldest remaining one — if `days > paymentTermsDays`, returns `409 { code: "OVERDUE_PAYMENT", overdueDays, paymentTermsDays, outstandingAmount, oldestUnpaidInvoiceDate }` with an Arabic explanation. Cash invoices, customers with `NULL`/`0` terms, and POS walk-in (no customerId) bypass the guard. Field is editable on `/customers/new` and `/customers/:id` under the "الائتمان والمسموح به" section next to `creditLimit`/`enforceCreditLimit`.
- **Production Routes — Literal Sub-Segments Before `/:id`**: Same Express 5 / path-to-regexp 8 quirk as sister-companies. In `routes/production.ts`, `router.get("/orders/pending-approval", …)` MUST be registered BEFORE `router.get("/orders/:id", …)` — otherwise `:id` swallows `"pending-approval"`, `Number(req.params.id)` → `NaN`, and the `/:id` handler 500s (invalid SQL bind). The `/:id` handler also now guards `Number.isInteger(id) && id > 0` → 400 to avoid the same trap for any other malformed literal. When adding more literal `/orders/<word>` endpoints in this file, register them above line ~553.
- **Production Order Post-Issue Lock**: Once a production order moves to `in_production`, the WIP setup fields (raw warehouse, WIP/raw-inventory/labor/overhead accounts, labor & overhead amounts) become read-only via PATCH guard. Changing them after the issue JE has posted would corrupt the WIP balance because the receipt JE would credit a different WIP account than the issue debited. To change them, cancel the order (which auto-reverses the issue) and re-do the cycle. FG-side fields (FG warehouse, FG/variance/waste accounts, costCenter) remain editable until completion.
