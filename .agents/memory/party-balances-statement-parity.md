---
name: Party balances ↔ statement parity
description: Supplier/customer balances reports must replicate the statement formula exactly; invoice payment-status mirrors the settlement engine.
---

**Rule:** أرصدة الموردين/العملاء pages read the bulk `/purchases-analytics/supplier-balances` and `/sales-analytics/customer-balances` endpoints, which replicate the statement (كشف حساب) closing formula verbatim — RAW document amounts, NO exchange-rate conversion (the statement itself sums document currency), display-only parties excluded, and both sides add direct-JE net only on uniquely owned AP/AR accounts. Never repoint these pages to the aging endpoint (a third formula) or `/customers/balances`.

**Payment-status reports** (`/invoice-payment-status`, purchases + sales): `paid` mirrors the settlement engine — voucher lines (PV lines amount+tax, RV lines amount only) + header-linked vouchers not line-linked + settlement_links × source rate + legacy JE header links, all base currency, POSTED sources only (deliberate divergence from the engine's draft+posted cap). Lines and links from the SAME voucher are BOTH counted by design — links are minted only from the voucher's unallocated residual, so this is not double counting. Paid sources are invoice-scoped, not branch-scoped (payments follow the invoice).

**How to apply:** any new balances/paid computation must copy the statement or `lib/invoiceSettlement.ts` math, not invent a fourth formula. Preserve existing entity-linked voucher totals; for legacy vouchers with no entityId, supplement only their actual invoice-linked allocations (line amounts, tax where applicable, and settlement residuals), deduped by source row. Use a header amount only when no allocation rows exist. Simple and detailed party statements must emit direct posted JEs plus in-range vouchers and include both in opening balance; exclude document-generated JEs already represented by invoice/return/voucher rows. Never attribute an account-level JE when multiple parties share that account. Sales/purchase operational reports remain document-based; a manual JE changes the ledger, not invoice quantities, VAT, or sales/purchase KPIs. Frontend balance pages must render ONLY endpoint rows (never merge the full party list back in — that resurrects display-only parties with 0 balances).
